# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Sonoma is a Unity 6 (6000.4.4f1) project implementing a procedural terrain generation system using hierarchical heightmap-based terrain with quadtree LOD management. The system generates realistic natural landscapes from continent-scale down to third-person game scale with seamless LOD transitions.

**Current Status:** Milestones M0–M4 and M5a–M5b of `SonomaRevisedPlan.md` are done, and M5c, erosion, is planned (`Docs/M5_MacroLayer_Plan.md`, the M5c amendment) and not started; that document supersedes the 5-phase roadmap below and is what to work against. The synchronous prototype is gone: generation runs as Burst jobs behind a priority scheduler, heights come from a pure double-precision function, and seam stitching was deleted rather than fixed. M3a added subdivision (`LodMath`, `LodSelector`); M3b added the vertex-shader geomorph across all four passes, so LOD transitions no longer pop and skirts are down to their intended role — the fallback for transient states where the tree is briefly more than one depth apart across an edge. M4 took the system to planetary scale: M4a added the Earth-scale configuration (`EarthTerrainSettings.asset`: depth 19, 24 octaves, `SplitFactor` 3, a node-relative skirt) and the pure tests that pin it; M4b added `WorldOriginSystem.Tracked`, the thousand-rebase exactness test and the `EarthStress` scene, a 6371 km sphere to fly down from orbit. Six scenes: `SampleScene` (a 300 m sphere, the M3 reference, not to be retuned) and five stress scenes, each with its own `TerrainSettings` asset in `Assets/Settings/`. They are `EarthStress`; `SmallPlanetStress`, a cube sphere of a quarter Earth's radius (1,592.75 km, depth 17); `RingworldStress`, the inside of a ring of that radius 1,250 km wide (a cylinder of 8 × 1 roots, depth 16); `NarrowRingStress`, a ring of three quarters that radius (1,194.56 km) and 0.15 the width, 187.5 km (40 × 1 roots, depth 14, added last; `HeightScale` 4,000 gives it about the ring's relief in metres, and it runs the ring's LOD policy at a budget of 4,900 over a flattened worst case of 4,324); and `TerrariumStress`, the inside of a cylinder 10 km in radius and 30 km long (8 × 4 roots, depth 9). The three after Earth were added after M4, are the first scenes to run the cylinder topology at all, and share Earth's LOD policy (`SplitFactor` 3, `PreloadFactor` 1); `StressSceneTests` derives and pins their numbers. **M5a** (plan `Docs/M5_MacroLayer_Plan.md`) fills in `MacroSample`. It adds a persistent pyramid of maps per root quad, built by a Burst job at startup and read bicubically in both sample jobs, whose base height is added to the terrain. All the stress scenes have one (`EarthMacro.asset` and its siblings); `SampleScene` has none and is bit-identical to M4. **M5b** is done too: biomes are in (four `BiomeDefinition`s classified per vertex from climate, scaling the detail noise band by band, and reaching the shader as morphed weights under the stress scenes' `TerrainBiomes.mat`), and the relief spectrum is retuned: persistence 0.7 above 5 km and about 0.5 below, which gives hills and mountains of hundreds of metres over 5–100 km and 10 m features of 22–27 cm. That moved the two planets to `SplitFactor` 4 (budgets 9,400 and 8,300). On top of that, mountain belts: ruggedness scales only the 5–150 km band, ×0.3 on plains to ×3.3 in belts, which on Earth makes 5 / 20 / 100 km features 237 / 484 / 988 m in the belts. And the stress scenes have a sky (`_SONOMA_SKY`): ambient from the local up, and aerial haze. After M5b merged, the stress scenes' relief went up five times (Earth `HeightScale` 4,000 → 20,000, the others likewise, walking-scale roughness included, macro base heights unchanged), and the LOD carries it through `LodVertical`: selection and the morph measure distance in a world with every height scaled by `TerrainSettings.LodVerticalScale` (0.2 on the stress scenes, 1 on `SampleScene`), so the LOD relief allowance, `SplitFactor` and the planets' and the ring's budgets stay at M5b's figures.

## Core Architecture

### Coordinate Systems (Critical Concept)

The system uses **four coordinate spaces** with transformations between them:

1. **Quadtree Space**: Local [0,1] normalized coordinates per quadtree node
   - All generation algorithms work in this simple Cartesian space
   - Z-axis represents height/elevation

2. **Surface Space**: `double3` positions on the curved base surface
   - `SurfaceDef` describes the topology (cube-sphere, plane grid, cylinder); `RootQuad` is one root of it
   - `SurfaceMath.SurfaceFrame(surface, root, u, v, …)` evaluates position and normal analytically
   - Height is added along the surface normal; this is where the height function is sampled

3. **Local Render Space**: Camera-relative float coordinates
   - Used for actual Unity rendering to maintain precision
   - Origin rebases when camera moves beyond threshold (~1000 units)

4. **World Absolute Space**: Double-precision global coordinates
   - Tracks true position in large worlds
   - Prevents floating-point precision issues at scale

**Implementation Note:** Heights are sampled at **surface positions**, never in local quadtree coordinates — that is what makes two chunks agree wherever they touch. Chunk vertices are then stored relative to a per-chunk `double3 Anchor`, so their float magnitude never exceeds the node size, and `transform.position = (float3)(Anchor − WorldOrigin)` places them.

### Surface Parameterization (Critical for Curved Topologies)

Bilinear interpolation of Cartesian corner positions is only exact for flat planes. On a curved surface, interpolated corners drift off the true surface — the error grows toward the interior of a quad and compounds through subdivision, giving a faceted approximation rather than the true curve.

**Rule:** evaluate positions analytically from `(u, v)`, never by interpolating corner positions. `SurfaceMath` dispatches on a `SurfaceType` enum with a `switch` — never an interface or virtual call, because Burst cannot devirtualise those:

- **Cube-sphere** — `a = tan((2u−1)·π/4)`, likewise `b`, then `normalize(centre + a·right + b·up)` scaled by radius. The tangent adjustment cuts the worst-case cell spacing ratio from 2.733 to 1.621 (measured over 16×16 cells on a face) and leaves face boundaries untouched, since `tan(±π/4) = ±1`.
- **Plane grid** — `Origin + (u·TileSize, 0, v·TileSize)`; normal is always `+Y`.
- **Cylinder** — angle and z interpolated parametrically, then evaluated; normal points **inward**, for interior viewing.

This ensures child chunks at any subdivision depth conform to the true curved surface, not a flat facet of the root quad.

### Quadtree Spatial Hierarchy

- **Root nodes**: one per `RootQuad` — six on a cube-sphere, `Cols × Rows` on a plane grid or cylinder
- **Addressing**: integer `NodeId(Quad, Depth, X, Y)`, not float bounds. A node is addressable without walking the tree, and is usable as a dictionary key.
- **Child nodes**: each node subdivides into 4; each level is 50% of the parent's `(u, v)` extent
- **Typical depth**: 8–12 levels. Reaching 1 m vertex spacing on an Earth-sized cube-sphere needs depth 19 at resolution 33.
- **Status**: implemented in M3a. `LodSelector` descends from each root every frame, keyed on the branch containing the camera, so the wanted set is O(MaxDepth) deep rather than O(4^MaxDepth) wide. At the shipped configuration (`MaxDepth` 8, `SplitFactor` 4, `PreloadFactor` 1.15) the geometry alone wants **2946 nodes worst case over a face (at a corner), 2430 near a face centre**, and those counts are scale-free: a 300 m sphere and an Earth-radius one give the same figures. Terrain adds to them, because a node's bounding sphere is padded by half its relief, so rough ground splits further out: `SampleScene` wants **3546** worst case over all six faces, with the camera half a metre above its roughest ground. That is why `MaxResidentChunks` is 4000. It shipped at 3200, sized from the geometry alone, and the budget warning fired in the first play session. Every count is `6 + 4k` (six roots, then sibling groups of four), so that warning's "3202 wanted" meant only "over 3200", not the peak. The selector now also reports the session's peak working set when the terrain shuts down, every session — as a plain log under budget, a warning over it — which is the figure to size the budget from. (It first reported only sessions that overran, so a session that stayed under budget, the one that says how far under, printed nothing.) `WorkingSetTests.WorstCaseWorkingSetFitsTheBudget` pins the 3546, and `ConstantsMatchSampleScene` holds the test's copy of the configuration to the shipped asset, so reverting the asset fails a test rather than nothing.

### Generation Pipeline (Burst)

Chunks depend on nothing but their own `NodeId` — no parent, no neighbour — so they generate in any order, on any thread, and a cancelled one can simply be dropped.

**Stage 0 — Macro maps (startup, once).** `MacroMaps.Build` runs `MacroBuildJob` over every texel of every root quad's pyramid, applies the shared-edge copies on the main thread, and waits; `TerrainRoot` logs its size and build time. The maps are one persistent `NativeArray<float4>` that every sample job reads `[ReadOnly]`, disposed after the scheduler, whose `Dispose` completes those jobs. A scene without a `MacroLayerSettings` gets `MacroMaps.Disabled()`, one texel with `Enabled` false, because a job with an unconstructed `NativeArray` fails the safety check at schedule time.

**Stage 1 — Height sampling (worker thread).** `HeightSampleJob` (`IJobParallelFor`) over an `(R+2)²` grid: the chunk's own vertices plus a one-vertex border so normals are two-sided at the edge. `CoarseHeightSampleJob` does the even vertices at the *parent's* band limit, for M3b's geomorph targets. Each reads the macro maps at its vertex's `(quad, u, v)`, at `MacroLevel(depth)` and `MacroLevel(depth − 1)` respectively. Each job derives that level from its own node rather than taking it as a field, so no caller can leave it at 0. The coarse job's parent level is what keeps a fully morphed child equal to its parent once there is a base height. Output: `double3` base points, `float3` base normals, `float` heights.

**Stage 2 — Mesh building (worker thread).** `ChunkMeshJob` (`IJob`) writes `TerrainVertex` straight into a `Mesh.MeshData` obtained on the main thread, in chunk-local floats around the node's `Anchor`, and adds skirts.

**Stage 3 — Upload (main thread).** `Mesh.ApplyAndDisposeWritableMeshData` with `DontRecalculateBounds`; bounds come from the job's measured min/max height. The index buffer is a shared per-`(resolution, winding)` constant.

**Scheduler policy** (`GenerationScheduler`): priority queue keyed by `distance / NodeWorldSize` so near-and-coarse beats far-and-fine; in-flight jobs capped at `MaxInFlightJobs`; uploads bounded by `UploadBudgetMs` on a `Stopwatch`, **not** a chunk count, because upload cost scales with resolution.

### Height Function

Height is a **pure function of a surface position and a band limit** — same arguments, same bits, on any thread, in any order. That single property is what makes shared vertices agree without stitching, makes generation trivially parallel and cancellable, and makes the world reproducible from a seed.

There is deliberately **no parent→child heightmap chain**. Upsampling a parent and adding detail would force every chunk to depend on its whole ancestor chain, serialise generation top-down, forbid evicting ancestors, and *guarantee* that adjacent LODs disagree at shared vertices — which is what stitching then had to paper over. See `SonomaRevisedPlan.md` §2.5.

- **Double-precision lattice noise, all the way through.** `LatticeNoise.Gradient3D(double3, uint)` takes the integer cell with a `double` floor and keeps the fractional part, the fade, the corner dots and the interpolation in double; `Fbm` sums in double, and `TerrainHeightFunction.Height` narrows once, at the end. M2 narrowed the fraction to `float` because it is always in `[0,1)` — independent of distance from the origin, but **not of the octave's cell size**: 2⁻²⁴ of a 10,400 km cell is 0.62 m. See the Non-Obvious entry on axis-aligned lines.
- **Band-limited per depth.** `HeightParams.MaxOctave(d) = clamp(d + K0, 0, OctaveCount−1)`. A chunk carries only octaves its vertex spacing can represent, so a chunk and its parent evaluate deliberately *different* functions at the same point; M3b's geomorph bridges them.
- **Zero-mean**, so the base surface is the mean rather than a floor.
- **Macro layer in, not up.** `Height(p, maxOctave, macro, params)` adds `macro.BaseHeight`, a bicubic read of the persistent per-root-quad maps (M5a), and narrows once. The maps are a pyramid: level L has `(R − 1) × 2^L` texel cells across a quad, so its texel spacing is depth L's vertex spacing, and a chunk reads `MacroLayout.MacroLevel(depth) = clamp(depth, 0, LevelCount − 1)` — on texels, exactly, up to the top level. Each level is band-limited by truncating the macro octaves at four texels per wavelength. Channels: base height, temperature, moisture, ruggedness; no biome id. Non-local algorithms (erosion, rivers, tectonics) belong in the maps, run once and coarsely — never at chunk time. `default(MacroSample)` is "no macro layer" and returns M4's bits exactly.

### Seam Handling

Stitching is **deleted, not fixed**. Because height is a pure function of position, two chunks that share a vertex compute the same value:

- **Within a root quad: bit-identical.** `ChunkGrid.VertexUV` is the only place a vertex index becomes a surface parameter, and `UMax(x)` and `UMin(x+1)` are the same bits.
- **Across a cube edge: bounded, not identical.** The two faces reach the shared edge by different parameterisations, so positions differ by 2.067e-16 relative (1.32 nm at Earth radius) and edge *normals* by up to 0.151° — the border sample continues its own face's parameterisation past the edge rather than crossing onto the neighbour's, so the central difference is not centred. Geometric rather than terrain-driven: still 0.1503° at `HeightScale` 0. A faint shading seam along the 12 cube edges, not a crack.
- **The macro layer: bit-identical across every link.** Shared edge texels are written once and the read is exact under reversal (`MacroLayout.EdgeSource`, `MacroSampler`), so the base height adds nothing to the cube edges' 1.3 nm, and it holds whatever fills the maps.
- **Skirts** remain as the fallback for transient states: a neighbour up to three depths coarser (`ChunkMeshLayout.SkirtDepthGap`), with either side at any morph factor. That covers a parent the atomic swap holds at coarse LOD while its neighbour has gone three deeper, and two depths a morph window apart. Four or more depths apart is not covered.

### LOD Transition Morphing

Each fine vertex stores a morph target: the even vertex `(i & ~1, j & ~1)` evaluated at the parent's band limit, written by `ChunkMeshJob` into `TEXCOORD2` (position + depth) and `TEXCOORD3` (normal + elevation). `SonomaTerrainTriplanar.shader` reads them in **all four passes** and lerps position, normal and elevation by `k = saturate((dist − start_d) / (end_d − start_d))`, with `(start_d, end_d)` coming from the `_SonomaMorphRanges` global array that `TerrainRoot.PushMorphRanges` sets each frame.

`end_d` is the split distance of depth **d−1**, not of depth d: a chunk finishes morphing where its *parent* takes over, not where it hands over to its own children. `SplitFactor` and `MorphStartFraction` are bound together by `LodMath.MaxMorphStartFraction`, which is why the defaults are 4 and 0.15 rather than the plan's 2 and 0.4.

Fully morphed, a child mesh is triangle-for-triangle its parent: three of every four child cells collapse to zero area and the fourth reproduces a parent cell with the same winding. That is why the `(i00, i11, i10), (i00, i01, i11)` triangulation is load-bearing and must not be changed to a flipping scheme. `GeomorphTests.ChildAtFullMorphEqualsParent` asserts both halves — that each morph target *is* the corresponding parent vertex, and that the surviving triangles are the parent's index for index.

### Chunk Unloading

When resident chunk count exceeds budget: evict furthest first, in **complete sibling groups of four** — evicting a single node would leave its region uncovered. `ChunkPool` recycles the GameObject and its Mesh rather than destroying them; meshes are never destroyed during play. Implemented in M3a as `LodSelector.EvictToBudget`, which collapses a group into its already-resident parent. The collapsible groups are gathered in one pass and then drained furthest-first from a cached per-node distance; a group that becomes collapsible only because its own children have just gone waits for the next frame.

`TerrainRoot` is the scene entry point: it owns the `SurfaceDef`, the `ChunkPool`, the `GenerationScheduler` and the `LodSelector`, and drives them once per frame — selector first, then scheduler.

## Technical Specifications

### Performance Targets
- **Frame Budget**: < 2ms per frame for all terrain updates. **Not met yet.** `TerrainRoot.Update` measured a median 5.85 ms (p99 8.2) near the ground on `EarthStress`, in a Mono development build. That cost is the selector's per-frame walk over the working set, not generation, which runs on worker threads. M6.
- **Generation Time**: Chunks ready before player arrival at max camera velocity
- **Memory Budget**: `MaxResidentChunks`, sized above the measured worst-case working set *including* the terrain's relief pad — 4000 for `SampleScene` (worst case 3546), 9400 for the Earth configuration at `SplitFactor` 4 (15% over a worst case of 8,198, geometry only, from a replica `LodSelectorTests.EarthReplicaWantsWhatTheSelectorWants` holds to the real selector, and 12% over 8,394 with every node padded by a tenth of its size, which overstates the mountains' relief pad; at `SplitFactor` 3 it was 5,800 over 5,118, and a descent from orbit peaked at 4,430), 8300 for `SmallPlanetStress` (also `SplitFactor` 4, over 7,206, 7,386 padded), and about 13% over each other stress scene's worst case, measured by the same replica (`RingworldStress` 5600 over 4944, `TerrariumStress` 3600 over 3124); about 98 KB of vertex data each at resolution 33. Those are M5b's unflattened figures. In the world `LodVerticalScale` 0.2 flattens them to, the replica's worst cases are 8,286 on Earth, 7,466 on the small planet and 5,000 on the ring, all within their budgets, and 3,880 in the terrarium, whose budget rose to 4400 for it (see the `LodVertical` entry)
- **Visible Triangles**: 50K-500K depending on LOD

### Mesh Specifications
- **Vertex Format** (`TerrainVertex`, 80 bytes): `POSITION` float3, `NORMAL` float3, `COLOR` UNorm8×4 biome weights, `TEXCOORD0` UNorm8×4 morph-target biome weights, `TEXCOORD1` float4 `(topoUp.xyz, elevation)`, `TEXCOORD2` float4 `(morph position.xyz, depth)`, `TEXCOORD3` float4 `(morph normal.xyz, morph elevation)`. The two splats took the eight bytes of a float2 uv nothing read (M5b), and `COLOR` sits before `TEXCOORD0` because Unity wants a stream's attributes in `VertexAttribute` enum order.
- **Typical Resolutions**: 33, 65, 129 vertices per chunk edge. Must be **odd** — the geomorph target sub-grid is the even-indexed vertices, and an even resolution leaves it half a vertex out of step. Enforced in `HeightParams.Create`.
- **Index Format**: 16-bit, valid up to resolution **253** — the constraint is distinct vertices (`R² + 4R ≤ 65,536`), not triangle count. 32-bit is not implemented; `HeightParams.Create` refuses anything larger rather than letting it fail later inside the scheduler.
- **Counts**: `R² + 4R` vertices (grid plus one skirt row per edge), `2(R−1)² + 8(R−1)` triangles. At R=33 that is 1,221 vertices and 2,304 triangles.

### Data-Driven Configuration
All generation parameters should be ScriptableObjects:
- **Global Settings**: World scale, quadtree depth, generation distances
- **Per-Level Settings**: Chunk resolution, visibility distance, noise parameters
- **Biome Definitions**: Height ranges, slope constraints, vegetation density curves

## Important Design Decisions

1. **Heightmap-Based Only**: No voxels or overhangs (caves/overhangs are future work or handled with separate meshes)
2. **Deterministic Generation**: Same seed → same terrain (important for networking/saves)
3. **Collision Meshes**: Use simplified versions of visual mesh (separate LOD chain)
4. **Water Bodies**: Separate system, not integrated into heightmap
5. **Static Terrain**: No runtime deformation or destruction in initial implementation

## Non-Obvious Implementation Details

- **The topologies disagree on the handedness of `(u, v, normal)`, and it decides triangle winding.** Measured `dot(cross(du, dv), n)` is **+2.467e-2** on every cube face but **−1.0e-4** on a plane grid and **−7.854e-4** on a cylinder. One fixed vertex order therefore cannot face outward on all three: the prototype's triangulation was written for a plane, and a cube-sphere built with it renders **inside out**. `SurfaceMath.UvFrameIsRightHanded` classifies it and `ChunkMeshLayout.BuildIndices` takes it as `flipWinding`. Vertex normals do *not* use the flag — `ChunkMeshJob` orients them with `dot(n, baseNormal) < 0`, which is correct on any topology without one. Two tests guard this; the classification switch is re-derived numerically, as with the adjacency table.
- **The LOD thresholds must come from depth too, and for the same reason.** `LodMath.NominalSize(d)` is `S0 / 2^d`, never `SurfaceMath.NodeWorldSize`. Measured size varies across one cube face at a fixed depth — 1.1793:1 at depth 3, 1.2908 at depth 5, 1.3279 at depth 8 — so measured thresholds do not nest by exactly 2, and two same-depth nodes on one face end up at different points in the morph: at depth 8 the smallest is at `k = 1.000` where the largest is still at `k = 0.383`. That 0.617 disagreement along a shared edge is a gaping crack, and no amount of shader work recovers from it. Only the *threshold* is depth-only; the distance `LodSelector` compares against it still uses the node's real bounding sphere. `SonomaRevisedPlan.md` §4.4 originally said measured; it was corrected during M3a. Note the plan's phrasing "two same-depth neighbours at a shared edge" for the 0.383 figure: immediately adjacent nodes differ far too little to show it (worst measured disagreement 0.0000), and the number is the face's extremes. `LodMathTests.MeasuredNodeSizeWouldBreakTheBoundary` reproduces it.
- **`LodMath.NominalSize` divides by a shifted power of two, not by `math.pow`.** `MorphRangesNestExactly` asserts `end_{d-1} / end_d == 2.0` with a delta of zero, and it can only do that because `S0 / (double)(1L << d)` is exact in IEEE. This is the same species of decision as `HeightParams.FloorLog2` reading the exponent field rather than calling `log2`.
- **A node's bounding sphere is MOVED by the terrain, not inflated by it — and the difference is the whole LOD hierarchy.** The distance lives in `LodMath.NodeDistance`, static and pure, which `LodSelector` and `WorkingSetTests` both call; a test-side copy of it is how a working-set figure drifts from the selector it claims to measure. It originally padded the radius with `max(|MinHeight|, |MaxHeight|)`, the *absolute* elevation. That bounds the geometry correctly but grows without limit relative to the node, because elevation is fixed while the node halves each level: measured on `SampleScene` (a 300 m cube-sphere with `HeightScale` 50) the pad reached **10.5× the node size at depth 7 and 21× at depth 8**, so every node within ~40 m of the camera returned distance 0 and the tree split to `MaxDepth` everywhere regardless of where the camera was. Centring the sphere on the node's own mid-elevation and widening it by *half its relief* keeps it proportional: on the same scene the pad at depth 8 is **0.16 of the node size on average and 0.60 at the roughest node on all six faces**, against 21× before. It still creeps up with depth (next item), but slowly rather than doubling a level.
- **Terrain roughness spends the same boundary budget as node size spread, but it is checked at runtime, not by `LodMath.Create`.** The half-relief pad enters the boundary condition exactly where `SizeSpread` does, so `LodMath.MaxHalfRelief(depth)` inverts `MaxMorphStartFraction` for it. It is deliberately *not* a `Create`-time throw: fbm relief at a given scale is a property of the noise, not the configuration, so `LodSelector.OnChunkReady` warns instead, naming the measured relief, the allowance and the levers, on the first chunk to overrun, and the selector names the roughest chunk when the terrain shuts down. Measured over **every node at every depth on all six faces**, `C = halfRelief / (nodeSize × HeightScale/S0)` is independent of radius but **not flat across depth**: at persistence 0.5 each octave coarser than the node adds the same slope, so the mean climbs from 1.03 at depth 3 to 1.53 at depth 8 and the worst node from 2.16 to **5.89**. It is flat at persistence 0.4 (worst 2.31, face 0, depth 8) and grows roughly as `(2·persistence)^depth` above 0.5 (12.5 at 0.6, 32.9 at 0.7, same face and depth). For `SampleScene` that worst node needs **0.601 of the node size**; `SplitFactor` 4 with `MorphStartFraction` 0.15 allows 0.415, overrun at depths 6–8 by up to 45% (886 of ~516k nodes). Its asset therefore runs `MorphStartFraction` **0.09**, which allows 0.655 — 8% to spare at the worst node — while the C# default stays 0.15. A lower `MorphStartFraction` narrows the morph window; that is the price. `TerrainReliefTests` pins the worst node per depth by address, re-derives one full-face maximum, and asserts the configuration in both directions. `LodMathTests.MaxHalfReliefInvertsTheMorphStartFractionBound` pins the inversion, and `LodBoundaryTests` pads its simulated selection by exactly `MaxHalfRelief` — so if the inversion were wrong in the unsafe direction, boundaries would open at precisely the relief it permits and the boundary test would fail.
- **Measure a relief tail over the whole population, never a sample — and read an overrun as a warning, not a crack.** M3 recorded the persistence-0.5 constant as 3.15, from 49 nodes per depth on one face sampled 13×13 rather than 33×33: the 98.8th percentile of the depth-7 population. It chose `SplitFactor` 4 against that "with 23% to spare", and the first play session's warning fired. The Editor.log figure (1.77 m against 1.59 m at depth 7) was only the *first* chunk to overrun, since the warning fired once and nothing reported the worst; the worst depth-7 node is 2.07 m. Both warnings now keep their worst case and report it at `LodSelector.Dispose` — `LodSelectorTests.BudgetReportNamesThePeakNotTheFirstOverrun` and `ReliefReportNamesTheRoughestChunk` — so the next scene gets the number to retune against from one play session instead of an offline scan. `TerrainReliefTests.TheOriginalSampleMissedTheTail` reproduces the 3.15. The bound itself is conservative, because it stacks the largest node-size spread, full hysteresis and the roughest relief on one boundary. Simulating selection over `SampleScene`'s real terrain at the overrunning `MorphStartFraction` 0.15 (9,600 cameras ringed round the 400 roughest nodes, each side's morph distance taken to its own vertex) found **no** cross-depth sample disagreeing on effective LOD in 31.8M. The same simulation does break at `SplitFactor` 3 (677 samples) and at `HeightScale` 100 (1,719). `SampleScene` was retuned anyway, so the warning still means something when it fires.
- **`MorphStartFraction` above 0.5 cracks every LOD boundary in the world.** The fine side reaches `k = 1` at `end_d`; the coarse side stays at `k = 0` until `start_{d-1} = 2·end_d(1 - frac)`, so `frac <= 0.5` follows directly. `LodMath.Create` throws rather than letting it ship, and 0.5 exactly is accepted — an off-by-one there would cost a usable configuration.
- **`LodMath.cs` imports no `UnityEngine`; the `TerrainSettings` overload of `Create` lives in `LodMathSettings.cs`.** `TerrainSettings` is a `ScriptableObject`, so a single-file `LodMath` would drag `UnityEngine` in and lose the out-of-Editor harness. Same split, and same reason, as `ChunkMeshLayout` / `ChunkMeshBuffers`.
- **The per-frame order is selector, then scheduler, and chunks arrive hidden.** `LodSelector.OnChunkReady` deactivates the chunk it is handed and leaves it to the next `Run` to show. Landing a chunk visible would put a freshly generated child on screen in the same frame as the parent it replaces, which is exactly the overlap the atomic swap exists to prevent. The cost is one frame of latency on a new chunk; the parent is still drawing, so there is no hole.
- **The selector's split decision is `Descend`'s return value, not a stored flag.** A node goes into `_frameSplit` only when all four children returned covered, recursively; the visibility pass then descends only through `_frameSplit`. `NodeState.HasChildren` is a separate thing — last frame's split *decision*, kept solely to feed hysteresis. Conflating the two gives a node that is marked split before its children exist, and the visibility pass walks into a hole.
- **`ChunkPool.Dispose` destroys the GameObjects as well as the meshes, and uses `DestroyImmediate` outside play mode.** `Object.Destroy` defers to the end of the frame, which never arrives in an EditMode test — it throws there instead. `LodSelectorTests` drives the real pool, so the teardown path has to work in both.
- **A float fraction of a noise cell draws axis-aligned lines at planetary scale, so the noise is double from cell to sum.** The fraction `p − floor(p)` is in `[0,1)`, so a float holds it to 2⁻²⁴ *of a cell* — and a cell is as wide as its octave. On an Earth-radius sphere octave 0's cell is 10,400 km, 2⁻²⁴ of it 0.62 m: octave 0 became a staircase with 0.62 m treads along each world axis (octave 1 with 0.31 m treads, and so on to about octave 16). The risers are about a millimetre, invisible on rough ground; but Earth at `HeightScale` 9000 has metre-scale slopes of a few thousandths, and flying low in `EarthStress` the shading drew the steps as long straight lines converging on the horizon whenever the view ran along a lattice plane. A hillshade of the bare height function showed column striping 68× row striping along `x = const` at 0.5 m sampling; in double it is 0.98. Narrowing each octave's *value* to float is the same error along contours (octave 0 × 9000 m × 2⁻²⁴ = 0.5 mm), so `Fbm` sums in double too and `Height` narrows once. What remains is the stored float height's own ULP — 0.06 mm at 800 m, 0.5 mm at 5 km — which is noise, not lines. `HeightFunctionTests.EarthScaleHeightHasNoAxisAlignedSteps` is the guard (a float fraction fails it; `PrecisionDoesNotCollapseAtLargeCoordinates`, stepping 1e-3 of a cell, never could). Measured in managed code the double path costs no more than the float one; Burst's cost has not been measured.
- **The band limit must come from depth, never from measured node size.** `HeightParams.MaxOctave(depth)` is `clamp(depth + K0, 0, OctaveCount-1)`. Actual node size varies across a cube face by up to 1.33:1 at a fixed depth, which can straddle a `floor(log2(...))` boundary and give two same-depth neighbours different octave counts — different functions along a shared edge, i.e. a crack. `K0` is read off the IEEE exponent rather than via `log2`, because the reference config lands on exactly 16 and a library log returning 3.9999999999999996 would drop an octave worldwide.
- **The macro maps are a pyramid read by depth, for the octaves' reason.** One map per quad has the texel spacing of one depth, so every coarser chunk would point-sample content it cannot carry — aliasing, at exactly the depths seen from orbit. Level L's spacing is depth L's vertex spacing, and `MacroLayout.MacroLevel` takes a depth, never a measured size, so same-depth neighbours read the same level. Each level holds only the macro octaves of at least **four** texels' wavelength (Catmull-Rom rings near Nyquist), with the limit read off the exponent as `K0` is: at Earth, resolution 33, the ratio is exactly 8. `MacroLevel(d) ≤ d` is also what keeps a sample job's one-vertex border within one texel of the edge. The one read that goes further is the coarse job at depth 0, whose grid runs two depth-0 vertices out and reads level 0, so it lands two texels out. That read is drawn, because roots morph towards their coarse targets from far out (`LodMath.MorphRange(0)`). So the stored border is **three** texels and the sampler's cell clamps to −2 … n + 1, which lands every read on a texel. At two, it extrapolated with weights (2, −3, 3, −1) and tilted the coarse normals along every root-quad edge seen from orbit. `MacroTests.MacroReadIsExactOnTexels`, `MacroLevelIsDepthOnly` and `MacroLevelsAreBandLimited` pin it.
- **Macro samples agree across a root-quad edge to the bit, by construction — and the textbook Catmull-Rom loses it.** A read near an edge uses one quad's texels, so both quads must store the same edge texels, or the *base* height cracks, kilometres of it. The lower-indexed quad owns each edge row, including its one-texel extension past each corner, and the other copies it through `SurfaceMath.QuadEdgeLink`. A corner comes from the lowest of the three (cube) or four (grid, cylinder) quads sharing it. Every copy's source is a texel nothing copies into, so `MacroLayout.EdgeCopies` applies once, in any order. The read is then exact under a reversed link only because the weights are written `(g(1−t), h(1−t), h(t), g(t))` and summed `(w0p0 + w3p3) + (w1p1 + w2p2)`. The textbook `w0 = (−t³ + 2t² − t)/2 …` summed left to right is algebraically equal and disagrees on 16% of reversed-link samples at depth. **Only at depth, though:** a few depths past the top level every product is exact in double and the textbook form passes, so `MacroEdgesAgreeAcrossEveryLink` samples reversed links down to depth 24, where Earth's real 16-bit fractions live. It fills the maps with random texels, because the rule has to survive erosion writing them, and assumes `R − 1` is a power of two, which makes `1 − u` exact.
- **The macro maps hold climate, never a biome id.** A bicubic read of a categorical field is meaningless: halfway between desert (2) and tundra (4) it reads grassland (3). The channels are base height, temperature, moisture and ruggedness, and biomes are classified per vertex from the interpolated climate (M5b, `Biomes.Classify`). The weights are inverse-square climate distance raised to an integer sharpness and normalised. They are taken relative to the nearest biome, so nothing overflows, and a small floor on the distance keeps them finite and continuous through a biome's own centre. A nearest-biome rule, or a kernel with finite support, would cut a hard edge. The distance scales decide which axis dominates. At a `MoistureScale` of 0.25, moisture's 0–1 range weighed as much as 60 °C, and cold, wet ground classified as half rainforest. At 0.5, cold is tundra at any moisture, and `BiomeTests.ShippedBiomesFollowClimate` holds the table to that. The planet scenes' south pole is on the night side of their sun, so it reads darker and greener than it is. To tell climate from lighting, look at the macro map export's `<scene>_biomes.png`.
- **Biomes scale the detail noise by octave band, and ruggedness scales only the mountain band (C7).** Each biome gives an amplitude per band, low, mid and high, whose edges are wavelengths in metres (`MacroLayerSettings.LowBandEdge` and `MidBandEdge`, turned into octave counts by `HeightParams.WithBands`, by exponent). Ruggedness scales the mid band alone on top. Both are stored as gains relative to one (C5), so a default biome or a 1..1 ruggedness range is the identity, and with zero gains `TerrainHeightFunction.Height` runs the original `Fbm`. The shipped biome amplitudes are all at most 1.
  - **The mountain belts.** On the planets and the ring the band edges are 150 km and 5 km, so the mid band is the octaves of 5 to about 100 km, and ruggedness runs it from 0.3 on plains to 3.3 in belts. `RuggednessCentre` 0.2 (stored as a shift from 0.5, C5) shapes the map: on Earth 11% of the surface is full belt, 35% is at twice the amplitude or more, and 30% is plains under 0.6. `MacroTests.MountainBeltsAreAMinority` pins those shares. The terrarium keeps 2 km and 50 m, and a range of 0.5..1.
  - **Why not the high band too.** Ruggedness used to scale the mid and high bands together, up to 1.44. A band's relief cost per metre of height falls with its wavelength, and the fine band was most of the LOD relief demand. Leaving it to the biomes paid for a ×3 mountain band: Earth's demand went from C 526 × 1.44 to 674 measured with the belts in.
  - **How the tests price it.** The relief demand no longer scales with a single largest amplitude. Each scene's C is measured with the bands at amplitudes at least `MacroParams.MaxBandAmplitude`, (1, 3, 1) on the planets and the ring. `MacroTests.DetailDemand` asserts the asset stays under the amplitudes C was measured at, so raising one fails a test until C is re-measured.
- **Splat weights morph, like elevation, and ride where the uv was (C6).** Fully morphed, three of every four child cells collapse and the survivor is drawn at the even vertices, so shading it with the fine vertices' own weights would pop colour at every swap. The coarse sample job computes weights at the parent's macro level, the mesh job puts the even vertex's in `TEXCOORD0`, and ForwardLit lerps `COLOR` towards it on the morph's k. `GeomorphTests.ChildAtFullMorphEqualsParent` holds the morph target's weights to the parent's byte for byte, over a real macro layer with biomes. The shader path is the local `shader_feature` `_SONOMA_BIOMES`, on only in `TerrainBiomes.mat`, which the four stress scenes use; `SampleScene`'s material never compiles it. The colours are the global `_SonomaBiomeColors[4]`, pushed by `TerrainRoot` with the morph ranges.
- **The sky path lights by the local up and hazes by altitude, because a planet's up is not world Y (M5b).** A directional light shows gentle relief only near the terminator; elsewhere a 10° slope changes N·L by a few percent. `_SONOMA_SKY`, a local `shader_feature` in ForwardLit, on only in `TerrainBiomes.mat`, adds the cues that work at any sun angle.
  - **Ambient.** It comes from `TerrainSettings.SkyAmbient` and `GroundAmbient` by `(1 + N·topoUp) / 2`, the hemisphere a tilted surface faces. URP's world-space SH has its up along world Y, which is the local up only at a planet's north pole. The term is physical, so it is subtle on gentle ground: a 15° slope is under 2% darker.
  - **Haze.** Aerial perspective is the strong cue: transmittance through an exponential atmosphere, `HazeVisibility` (Koschmieder: density 3.912 / V) and `HazeScaleHeight`, towards the haze colour lit by the sun on the day side and by the sky alone on the night side. The optical depth is integrated in four steps with the altitude linear within each, which integrates exactly per step. So a path that climbs out of the air, across a ring to its far side or down from orbit, is charged about `len × H / climb` per step rather than the base density all the way; a midpoint rule charged the ring's far side for 3,000 km of sea-level air. Four steps undercount grazing paths over a sphere's horizon, which are hazed out anyway.
  - **Altitude.** It is computed in the shader from absolute positions, `positionWS + _SonomaWorldOrigin`, and the surface's type and radius (`_SonomaSurface`). That stays consistent through a rebase because `ShiftOrigin` re-pushes the origin. The haze measures from `_WorldSpaceCameraPos`, which is right in ForwardLit, a camera pass, and wrong only in the shadow passes the morph has to avoid it in.
  - **Rock.** The material's rock threshold is 0.04 to 0.12 of `1 − N·up`, 16° to 28°; it was 0.55, 63°, which no slope reached.
  - **What it does not do.** Haze applies to the terrain only, not the skybox. The values are per scene and push every frame, so they can be tuned in the inspector during play.
- **The relief spectrum: the LOD relief allowance is a slope budget, and the spectrum decides where it is spent (C10).** At persistence 0.5 every octave is equally steep, with slope `HeightScale / S0`, so on a big world the terrain is gentle at every scale. Earth at M4's `HeightScale` 9000 had 10 m features of 0.9 cm and 5 km features of 4 m: millimetre-smooth up close, and flat from a kilometre up. Real relief falls off more slowly at large scales, with persistence around 0.7 above a few kilometres, and at about 0.5 below.
  - **The mechanism.** `TerrainSettings.RoughnessCrossover` (metres) and `FinePersistence` give two slopes, `Persistence` above the crossover and `FinePersistence` below it (`HeightParams.WithRoughness`, the crossover counted by exponent). A crossover of 0 is off, and a `FinePersistence` equal to `Persistence` is bit-identical to one slope.
  - **The tuning.** M5b first roughened only the small scales: fine persistence 0.7–0.8 below 250 m–1 km. The user saw 10 m bumps and still flat land from 500–1,000 m up. The stress scenes now run a mountain spectrum, persistence 0.7 above 5 km and about 0.5 below.
  - **The cost.** Kilometre-scale slopes are exactly what the boundary budget pays for. Measured C grows by an order of magnitude, and its tail is long: on Earth, 1,000 random nodes found a depth-19 half-relief of 0.082 of the node where 20,000 found 0.106. So each scene's C was re-measured on 20,000 random nodes per depth at its spectrum and pinned half again over the roughest (C10's method).

  - **Heights.** They are octave amplitudes before biomes; neighbouring octaves add. The belt column is the mid band at 3, about its largest (biome 0.9 × ruggedness 3.3); plains take it down to 0.3 of the plain figure. The 10 m features are the high band, which only the biomes scale, by at most 0.9. Every figure is five times M5b's, which the user found flat from altitude; walking-scale roughness was scaled with the rest on purpose, and the macro base heights were left alone.
  - **Why `SplitFactor` 4 on the spheres.** No `MorphStartFraction` carries this relief at `SplitFactor` 3, and `EarthConfigurationClearsTheReliefAllowance` asserts that. The cost is chunks: worst cases of 8,198 and 7,206 against 5,118 and 4,510, with budgets of 9,400 and 8,300. The user chose this for mountains, with a morph fraction of 0.10. With the belts Earth's 0.10 leaves a little to spare (it could go to 0.124), and the small planet's 0.12 very little (0.123). All of this is in the flattened world `LodVertical` measures in: at `LodVerticalScale` 0.2 the five-times relief costs the allowance what M5b's did. The true relief would need `SplitFactor` about 10 on Earth.
  - **The ring.** A cylinder's allowance is three times a sphere's, so the ring stays at `SplitFactor` 3. The belts would leave nothing to spare at 0.15, so it runs 0.14.
  - **Skirts.** A skirt is geometry and is not flattened. Each chunk's drop now comes from its own measured true relief plus the surface's chord sag (`SkirtFraction` 1, and 1.2 on the ring; see the `SkirtDepth` entry), so flat ground hangs a short skirt and a mountainside a long one. Until then `SkirtFraction` was node-relative, at twice the estimated true relief demand: Earth 2.9, small planet 2.8, ring 2.1, terrarium 2.1 (0.58, 0.56, 0.43 and 0.66 at M5b's relief). That padded every chunk's culling bounds by two to three node sizes, plains included, and at depth 0 and 1 hung skirts through the planets until the review capped them; the per-chunk rule needs no cap.
  - **Tests.** `StressSceneTests.CloseUpRoughnessMeetsItsTarget` pins each scene's 10 m feature height, an octave amplitude rather than a measured relief, so a retune that smooths the ground or roughens it past the measured C fails a test.
- **`LodVertical`: LOD selection and the morph measure distance in a flattened world, so five times the relief spends the allowance the original did.** The relief allowance is a slope budget (previous entry), and `HeightScale` multiplies every slope. At five times M5b's relief, Earth's demand is 1.30 of a node against an allowance of 0.61. Carrying that with `SplitFactor` would take about 10, roughly 37,000 chunks.
  - **The map.** A point moves along the surface normal by `−Flatten × (clamp(altitude, −E, E) − Anchor)`, where `Flatten = 1 − LodVerticalScale`. `E` is the height envelope, `TerrainHeightFunction.MaxAbsHeight`, a strict bound: Earth 84 km, the small planet 48, the ring 50, the terrarium 2.6. It is a bound only because it counts the bicubic macro read's overshoot of its texels, up to `MacroSampler.MaxOvershoot` (1.25² = 1.5625) of the largest; `MacroTests.MacroReadOvershootIsBoundedAndAttained` reaches it exactly. Inside the envelope altitudes scale by s. Above it a camera is shifted, not scaled, so orbit stays orbit. The selector's spheres (`LodMath.NodeDistance`), the camera (`TerrainRoot.LodViewPosition`, pushed as `_SonomaViewPosition` and handed to `Run`) and every vertex (`SonomaMorphFactor`: `positionWS − _SonomaLodVertical.x × (elevation − _SonomaLodVertical.y) × topoUp`, packed by `LodVertical.ShaderParams`) all go through the same map. The boundary proof only needs each vertex inside its own node's sphere, so it holds with the relief scaled by s. Morph targets and positions stay in the true world.
  - **Never coarser.** The map is 1-Lipschitz in altitude. The anchor is the envelope side nearest the centre of curvature (`−E` on a sphere, `+E` inside a cylinder, 0 on a plane), so it only moves points towards that centre. A flattened distance is therefore never longer than the true one, which `LodVerticalTests.FlattenedDistanceIsNeverLonger` checks on every topology. An anchor at 0 lengthens distances across a sphere slightly where terrain is below zero. Inside a cylinder it also throws a camera near the axis a whole `Flatten × E` towards whichever wall is nearer. `AnchorAtZeroWouldBeCoarser` keeps that mutation.
  - **The cost of the anchor.** It moves the flattened world towards the centre by `Flatten × E`, which shrinks it. That is 1% on Earth, 2.5% on the small planet and the ring, and a fifth of the terrarium's 10 km. The worst-case working sets are 8,286, 7,466, 5,000 and 3,880 flattened, against M5b's 8,198, 7,206, 4,944 and 3,124. The terrarium's budget rose from 3600 to 4400 for it; the others fit as they were. In float the anchor also puts both ends of the shader's distance about `Flatten × E` (68 km on Earth) from the render-space origin, a few millimetres of rounding: a k error under 1e-3, and sub-millimetre motion. Finer than needed, never coarser.
  - **Every pass reads `TEXCOORD1`.** The shadow, depth and depth-normals passes did not before. `GeomorphTests.ShaderMorphsInEveryPass` now checks `TEXCOORD1` and `_SonomaLodVertical`. An unset global reads (0, 0), the identity, and `TerrainRoot` pushes it every frame so one scene's map cannot leak into the next.
  - **Not flattened.** Skirts, culling bounds and the fly camera are true geometry, which is why a skirt is sized from its chunk's true relief. The geometric error at a given LOD is the true one, five times M5b's, so the morph's vertex motion is five times larger on screen. It is estimated at about a pixel at 1080p; judge it by eye. The relief warning and the roughest-chunk report judge the flattened relief, and say so.
  - **Evidence.** `LodVerticalTests` selects over real terrain, each node padded by its own measured height range, and checks every boundary vertex the shader morphs. At five times a relief that fits, flattened by 0.2, the roughest node spends the same fraction of the allowance and nothing opens. Unflattened, the same relief overruns the allowance. Cameras ringed at the split thresholds of the roughest nodes then open boundaries: 72 of 17.4M samples at 2.0x the allowance on a plane, and 9,251 of 18.6M at 4.7x on a sphere. None open flattened, over 16.6M and 24.5M samples. That run takes minutes and is recorded in the test, not run by it.
- **`MacroPyramid` derives a channel's lower levels by filtering down, and fills their borders from the neighbouring quad — never by continuing a function.** A channel nothing can generate level by level (the continent height, M5c's erosion correction) has its top level filled, then each level below is the one above filtered by the 5 × 5 binomial and taken at the coincident texels, `(i, j)` from `(2i, 2j)`. A derived level has no function to continue past its edge, so `MacroLayout.HaloSource` fills each border texel from the neighbour, through `QuadEdgeLink`. The neighbour's texel sits at the same position along the linked edge, reversal included, the same number of texels in. A cube-corner block takes the halo of the side texel on its South or North side, and a rim repeats its own edge texel. Every source is resolved through `EdgeSource` to the texel its owner stores, so the halo and the edge copies are gathers that read nothing either writes. Per level the order is decimate, halo, edge copies.
  - **The copies are load-bearing everywhere,** not only on the cube: without them the derived edges disagree on every topology, 60 to 672 samples in `MacroPyramidTests.DerivedEdgesAgreeAcrossEveryLink`.
  - **The halo is exact inside a cylinder or plane grid, and only near across a cube edge.** There the two faces' grid lines are different great circles off the edge line, so a border texel's continued point and its source are up to 0.57 texels apart per texel of depth over the middle half of an edge, and 1.0 at its ends, by the cube corner. That is harmless, because reads are exact on the edge line itself (C2) and nothing is defined at a continued point. Ignoring a link's reversal lands texels up to 25 texels off, which is the mutation `HaloReadsTheNeighboursOverlappingTexel` keeps.
  - **The filter.** Its weights are integers summed in double and divided once by 256, so a constant passes exactly. They are positive and rounding is monotone, so no output leaves the input's range, and an analytic height bound stays valid over a derived channel. It is not C1's truncation: on white noise the level below keeps 25.7% of its energy under four texels per wavelength (white noise has 50.4%).
  - **`MacroPyramidJob` is one single-threaded Burst job** calling the same static functions as the managed reference, so the two are bit-identical by construction; `MacroMapsTests.PyramidJobMatchesTheManagedPyramid` holds it.
- **`default(MacroSample)` must mean "no macro layer", and every field added to it must keep that true.** A default sample adds `BaseHeight` 0.0 and returns M4's bits, which is what keeps `SampleScene` and every relief figure pinned against it valid. A per-band amplitude stored as a multiplier would default to zero and flatten the world on whichever path forgot to set it, so M5b stores gains relative to one. `HeightIsBitIdenticalWithoutAMacroLayer` compares against frozen copies of M4's `Height` and `Fbm`. `BaseHeight` is a double so the height still narrows once.
- **The sample jobs always get a constructed macro array, and it is freed after the scheduler.** A job whose `NativeArray` field was never constructed fails the safety check when scheduled, before it can test `MacroParams.Enabled`, so a scene with no macro layer runs `MacroMaps.Disabled()`: one texel. `GenerationScheduler` makes and owns one when given none, and tests that schedule the jobs themselves pass one. `TerrainRoot.OnDestroy` disposes the maps after `GenerationScheduler.Dispose`, which completes the jobs reading them. In the other order the Editor throws and a build reads freed memory; `MacroMapsTests.MacroMapsOutliveTheJobs` checks both orders.
- **`TerrainRoot.HeightAt` includes the macro layer, through `SurfaceMath.Locate`.** Without it the fly camera understates the ground by the base height, kilometres, and sets its near plane to a hundredth of a clearance it does not have, into the ground. The maps are addressed by `(quad, u, v)` and the tool has a point, so `Locate` inverts the surface: the face by the largest axis then `atan`, the cylinder's column by angle, the plane's tile by `floor`. It is a tool path, good to about 1e-15 in `u`. A point on a shared edge may come back on either quad, which the macro's edge agreement makes harmless. The body is `TerrainHeightFunction.HeightAtPoint`, so `MacroTests.HeightAtReadsWhatTheChunksRead` tests the function itself rather than a copy. That test checks the result against what the chunks draw, and checks that reading level 0 or dropping the macro would fail it.
- **The macro layer's base height spends the LOD relief allowance too, and the tests size it.** The demand becomes `(C × HeightScale + C_m × BaseHeightScale) / S0` (`MacroTests.Demand`), where `C_m` = 7 is the macro's own relief factor, half again over the roughest of 1,000 sampled nodes a depth (4.70). Half-relief is subadditive, so the sum bounds the two together, conservatively, since it puts both worst cases on one node. The relief tests therefore ask 2× of the allowance against the detail estimate, as before, and `MacroTests.CombinedMargin`, 1.25×, against the sum. At M5b's relief the terrarium was the binding case: its 200 m of base height passed at 1.31×, and above about 220 m it failed. The flattened world (`LodVertical`) scales both terms by `LodVerticalScale`, so it now passes at 2.0×, still the least of the four, and would fail above about 1,100 m. Skirts once covered twice the TRUE sum as a share of the node; they are now sized from each chunk's measured relief, base height included (see the `SkirtDepth` entry).
- **`ChunkGrid.VertexUV` is the only place a vertex index becomes a surface parameter.** The exact `math.lerp(UMin, UMax, i / (double)(R-1))` is load-bearing: `UMax(x)` and `UMin(x+1)` are bit-identical, so both sides of a same-quad seam produce identical `double3`s and identical heights. Rewriting it as `UMin + (UMax - UMin) * t` is algebraically equal, changes the last bits, and silently turns an exact seam into an approximate one.
- **Configuration is validated once, in `HeightParams.Create`, and nowhere later.** Chunk resolution must be odd, at least 3, and no greater than `ChunkMeshLayout.MaxResolutionFor16BitIndices` (253). The upper bound matters as much as the others: without it an oversized resolution is accepted at setup and first fails inside `GenerationScheduler.Upload`, after the jobs have allocated their persistent buffers and on a path that has already dropped the `Pending` and so cannot free them.
- **`ChunkPool` owns every mesh it created, not just the released ones.** `Dispose` walks a `_all` list rather than the `_free` stack, because at teardown every live chunk is still checked out — a Dispose over the free stack alone frees nothing.
- **Seams are exact within a root quad and merely bounded across one — for normals as well as positions.** Across a cube edge the two faces reach the shared edge by different parameterisations, so the surface points differ by 2.067e-16 relative (1.32 nm at Earth radius). `SonomaRevisedPlan.md` §5 asks for bit-identical heights "including across a cube edge"; that half is unachievable. Skirts cover it. **Normals split the same way and by much more:** the `(R+2)` border sample continues *this* face's tangent-adjusted parameterisation past its own edge instead of crossing onto the neighbour's, so the central difference is not centred. Measured disagreement is **1.9e-6° within a root quad but 0.151° across a cube edge** — and it is geometric, not terrain-driven: at `HeightScale = 0`, on a perfect sphere, it is still 0.1503°. That is a faint shading discontinuity along the 12 cube edges, most likely to show in a specular highlight at a grazing angle; it is not a crack. `HeightFunctionTests.CrossFaceEdgeNormalsAgreeToABoundedAngle` pins both regimes. Do not describe edge normals as agreeing "by construction" without saying which side of a root quad boundary you mean.
- **The cube adjacency table is hand-entered but test-guarded.** `SurfaceMath.CubeEdgeLink` holds 24 entries, 8 of which reverse the along-edge parameter. `CubeAdjacencyTests` re-derives the whole table from the face basis and compares, so edit the basis or the table only with that test running.
- **Cube face basis for +Y and -Y looks wrong but isn't.** Faces 2 and 3 use `up = (0,0,-1)` and `(0,0,1)` respectively; those are what make `right x up == centre` hold for every face. "Tidying" them silently invalidates the adjacency table.
- **The topology class is `SurfaceMath`, not `Surface`.** A type may not share the name of its own namespace: from a sibling namespace such as `Sonoma.Core.Generation`, with usings above the namespace (the house style), the simple name `Surface` binds to the namespace `Sonoma.Core.Surface` and `Surface.SurfacePoint(...)` fails with CS0234. Renaming it back breaks every M2 caller.
- **`NodeId.Parent` throws on a root.** C# masks shift counts, so a `Depth` of -1 would make `Span` evaluate `1 << 31` == `int.MinValue` and the UV accessors return small negative values instead of failing. Use `IsRoot` or `TryGetParent` when ascending.
- **The surface layer refuses malformed arguments rather than absorbing them.** `FaceCentre`/`FaceRight`/`FaceUp` spell out face 5 and throw on anything outside 0..5; `CubeEdgeLink` validates face and edge *before* flattening them to `face * 4 + edge`, because an out-of-range edge otherwise aliases into the next face's row; `Neighbour` validates `NodeId.Quad`, `X`, `Y` and `Depth`. All the guard messages are compile-time constants so the throw sites stay Burst-compilable. This is deliberate and test-covered — the catch-all versions returned plausible-looking geometry for a bad quad index, which surfaces later as terrain in the wrong place instead of failing at the call site.
- **`RootQuad.Index` is the quad's position in the `BuildRoots` array**, for every topology (and, for a cube-sphere, also the face). `NodeWorldSize` takes both a `RootQuad` and a `NodeId` that already carries its quad, so it checks the two agree and throws if they do not — a mismatch would otherwise return a wrong-but-plausible size and quietly bias LOD.
- **`SurfaceDebugDrawer` bounds its own gizmo cost.** `OnDrawGizmos` runs per SceneView repaint, so `DrawDepth` is capped at 4 and `EdgeSegments` is scaled down to keep the total near `MaxGizmoLines`. Raising the depth costs curvature detail, not responsiveness; unbounded it issued ~393k `Gizmos.DrawLine` calls per repaint and locked the Editor.
- **`TerrainChunk` has two static sets**: `AllChunks` (every chunk, including `SetActive(false)` ones) and `AllActive` (only enabled). `WorldOriginSystem` iterates `AllChunks` so hidden chunks aren't missed during an origin rebase, and rebases each from its `double3 Anchor` rather than shifting by a delta — the prototype's `position -= shift` accumulated float error over a session. `WorldOriginTests.RebaseIsExactAfterAThousandShifts` asserts the positions to the bit, not within a delta, because a tolerance would hide exactly the drift being tested for; the prototype's form fails it on the first shift.
- **The camera must be a root object, and everything else in render space goes in `WorldOriginSystem.Tracked`.** A rebase sets the camera's world position to zero, which is right for a lone camera and wrong for one under a rig: the camera jumps and the rig stays. Tracked transforms are shifted by the same delta. Unlike chunks they have no double anchor, so they do carry float rounding across rebases — anything that must stay put to the millimetre over a long session needs a double position of its own. **There is one camera, and it is `WorldOriginSystem`'s**: `ViewCamera` there (empty means `Camera.main`) is the camera the world is rebased around *and* the one `TerrainRoot` selects and morphs from, through `WorldOriginSystem.ActiveCamera`. `TerrainRoot` had a `ViewCamera` of its own until M4's review; pointed anywhere but the main camera, a rebase moved one camera while the terrain measured from the other, a whole threshold off.
- **`WorldOriginSystem.WorldOrigin` is static and outlives its scene, so it is zeroed at play-mode boundaries — never by a component going away.** The Editor does not reload the domain on leaving play mode (and need not on entering it), so after an `EarthStress` session the origin would otherwise sit megametres out and the next session, or an EditMode test run, would place every chunk against a camera on the other side of the planet. `WorldOriginSystem.ResetOrigin` runs on entering play (`RuntimeInitializeOnLoadMethod`, for when domain reload is off) and on returning to edit mode (`Assets/Editor/WorldOriginPlayModeReset.cs`, which needs `UnityEditor`). M4 first did it in `OnDestroy`, which would have moved the origin under live terrain whenever the system was destroyed mid-session — an additive unload, a deleted object. Tests that set it save and restore it, and the shader globals with it.
- **A rebase has to move every render-space position, shader globals included.** `TerrainRoot.Update` pushes `_SonomaViewPosition` and the rebase lands in `WorldOriginSystem.LateUpdate`, before rendering, so as first shipped every rebase frame rendered chunks moved by −shift around a camera at zero while the morph still measured from the pre-rebase point, a threshold away. Invisible from orbit, where morph windows are hundreds of kilometres; near the ground, with windows of a few hundred metres, the near field popped to its parents' geometry for one frame per rebase — exactly the jitter M4 exists to rule out. `ShiftOrigin` now moves the global by the same delta, so it names the same absolute point the selector ran from that frame. `WorldOriginTests.ShiftCarriesTheViewPositionWithIt` holds it.
- **The rebase threshold scales with clearance where something reports it.** `RebaseThreshold` is the floor; `RebasePerClearance × ViewClearance` raises it, and `TopologyFlyCamera` reports the clearance. The error a rebase guards against is about 6e-8 of the camera's render-space distance from the origin, against a pixel at the nearest geometry of about 1e-3 of the clearance, so ten times the clearance stays under a thousandth of a pixel. At a fixed 1000 m, `EarthStress`'s descent at up to 50 km/s rebased every frame, each a pass over every chunk; it runs at 10. `SampleScene` leaves it at 0. Measured on a descent from orbit to the ground: **5 rebases**, about one per 11× fall in altitude as the rule predicts, the slowest 2.48 ms over 3,818 chunks in Editor play mode — about 0.65 µs a chunk, over the 2 ms terrain budget for that one frame, which is harmless five times a descent and would not have been once a frame. `WorldOriginSystem` logs that summary (count, rate, busiest second, slowest rebase) when play ends and marks each rebase `WorldOriginSystem.ShiftOrigin` for the Profiler. It times with `Stopwatch`, because Unity re-bases `Time.realtimeSinceStartupAsDouble` between entering play and the teardown on leaving it, and a duration measured across the two came out negative.
- **Triplanar texture coordinates are quantised to 0.5 m at Earth radius, and that is deliberately not fixed.** The shader samples `positionWS + _SonomaWorldOrigin`, a float the size of the world, so every fragment within half a metre samples the same texel and the pattern jumps by up to 0.25 m on each rebase. It is invisible only because `TerrainTriplaner.mat` has no textures. The fix — push the origin reduced modulo a large power of two, in double — tiles seamlessly only when every triplanar period divides the modulus, so **texture periods must be powers of two metres**; the current `_*Scale` of 0.05 is a 20 m period and would not qualify. Decide it with the textures. Recorded in the shader header and `SonomaRevisedPlan.md` §4.5.
- **A camera's far/near ratio above about 3.4e7 culls everything, silently.** Unity builds the projection matrix in float and extracts the culling frustum from it; `m22 = −(far + near)/(far − near)`, and once `far + near` rounds to `far` it is exactly −1 and the far plane's normal is zero. `EarthStress` first shipped at 0.3 m to 20,000 km (6.7e7) and drew nothing, with nothing in the log. The depth buffer is not the constraint — URP's default on Windows is 32-bit float, reversed Z — the frustum is. Keep ratios at or below 1e6, where the extracted plane is within 2%. No fixed pair serves orbit and ground on an Earth-sized sphere, so `TopologyFlyCamera.AutoClipPlanes` sets them per frame from the clearance (near = clearance / 100 with a 0.2 m floor, far = horizon bound capped at 1e6 × near). A hundredth, not a tenth: terrain *ahead* can be far nearer than the ground below, and a tenth cut open a ridge 300 m in front of a camera flying 3 km up; at the auto-speed a hundredth of the clearance is under a frame's travel, so only terrain the camera is about to hit is clipped. `EarthSettingsAssetTests.FlyCameraClipPlanesStayCullableAndTight` sweeps it from the ground to beyond orbit. `EarthSettingsAssetTests.SceneCamerasKeepACullableFrustum` guards both scenes.
- **Inside a cylinder, four things behave differently from a sphere, and none of them is a bug.** (1) *Lighting:* the shader has a main directional light and ambient only, and one directional light can light only the half of a cylinder's interior whose inward normals face it. `RingworldStress`, `NarrowRingStress` and `TerrariumStress` aim the sun onto the camera's starting floor and use flat ambient (`m_AmbientMode` 3) so the far half reads as shaded rather than black. Under the sky path the terrain takes its ambient from `TerrainSettings.SkyAmbient` instead, which does the same job. A sun on the axis needs shader work. (2) *The ring's arch:* a cylinder has no horizon, so the fly camera's far plane is only the `MaxClipRatio` cap, 1e6 × near; two metres up that is 200 km, so the far side of a 1,593 km ring overhead is culled near the ground and appears from higher up. Accepted for now; a second, far camera is the fix. (3) *Open rims:* a cylinder's ends are not terrain, so beyond the ring's edges and the terrarium's ends is the skybox. (4) *Working set:* everything inside a 10 km terrarium is within a few split distances of the camera, so all 32 roots subdivide and it wants 3,124 chunks at depth 9, more than a planet would at that depth.
- **`TopologyFlyCamera` scales speed by clearance above the terrain, not the base surface.** On an Earth-sized sphere with `HeightScale` 9000 the two differ by kilometres, so measuring from the base surface flew a camera two metres above a 5 km peak at 5 km/s. It samples the height function at full detail through `TerrainRoot.HeightAt`, and works out its absolute position in double: narrowing the origin to float first carries it to only 0.5 m at Earth radius.
- **A chunk finishes morphing where its PARENT takes over, not at its own split distance.** `LodMath.MorphRange(d).end` is `SplitDistance(d−1)` — written as `2 × SplitDistance(d)` so depth 0 needs no special case. A node's own split distance is where it hands over to its *children*; a chunk fully morphed there draws its parent's geometry while its coarser neighbour, also fully morphed, draws its grandparent's. `SonomaRevisedPlan.md` §4.4 and `Docs/M3_Geomorphing_Plan.md` both say "the split distance of depth d", and M3b shipped that first: measured against a simulated selection it put **100% of cross-depth boundary samples exactly 1.0 effective LOD apart**, which is a seam along every boundary and a full level of pop at every swap. `LodBoundaryTests` reproduces both the fix and the break.
- **The one number that says whether the terrain cracks is `depth − k`.** A chunk at depth d with morph factor k draws the geometry of depth `d − k`, so two chunks meeting at a surface point must agree on that value. Same-depth neighbours agree for free, because k is a function of the vertex's own distance. Cross-depth neighbours agree only when the fine side has reached `k = 1` and the coarse side has not left `k = 0`. Everything in `LodMathTests` checks the ranges against each other; only `LodBoundaryTests` checks them against an actual selected tree, which is why the off-by-one survived the first pass.
- **`SplitFactor = 2` cannot be used with the geomorph, and that is geometry, not tuning.** Selection uses a per-node bounding-sphere distance; the morph uses a per-vertex distance; a coarse leaf's patch reaches past its own sphere distance by up to `SurfaceMath.MaxNodeSizeSpread` nominal node sizes. That gives `MorphStartFraction ≤ 1 − (Hysteresis + SizeSpread / SplitFactor) / 2`, and at `SplitFactor 2` with any hysteresis on a cube sphere the ceiling is under 0.01 — a morph window under 1% wide, which is a pop by another name. `LodMath.Create` throws rather than let it ship. Cost scales with `SplitFactor²`: worst case over a face at `MaxDepth` 8 and `PreloadFactor` 1.15 the working set is 1898 chunks at 3 and **2946 at the shipped 4** on geometry alone, 2342 and 3546 on `SampleScene`'s terrain. What the extra buys is headroom for rough terrain — `SplitFactor` raises the `MorphStartFraction` ceiling *and* `LodMath.MaxHalfRelief` together. At 3, seven of `SampleScene`'s nine depths overrun the relief allowance, by up to 5.2×; at 4, three still do, by up to 45%, and `MorphStartFraction` 0.09 covers the rest.
- **The preload test is on the parent's distance, not the child's, and the difference is the whole feature.** `LodSelector.Preload` runs only on a node that did *not* split, so its distance is already at or beyond `SplitDistance(depth)`; a child's bounding sphere sits inside its parent's, so `NodeDistance(child) ≥ NodeDistance(node)`. M3a compared each child's distance against `PreloadDistance(depth + 1)`, which works out to `PreloadFactor / 2` of `SplitDistance(depth)` — 0.75 at the default 1.5, i.e. a threshold the parent had already exceeded. Measured out of Editor, that form preloaded **exactly zero nodes at every camera placement tried**, so every subdivision waited on four cold chunks while the atomic swap held the parent at coarse LOD. Nothing caught it because the selector is correct without preload — the tree converges, the swap stays atomic, coverage stays complete; the only symptom is latency. `LodSelectorTests.ChildrenAreRequestedBeforeTheParentSplits` is the assertion that was missing. Above about 1.2, preload is also the most expensive knob here: worst case over a face, with every split hysteresis can hold, the working set is 2734 chunks at `PreloadFactor` 1.0, 2946 at 1.15 and 4350 at 1.5 on geometry alone (3322, 3546 and 5226 on `SampleScene`'s terrain). Up to `HysteresisFactor` the margin is nearly free, because a node held split by hysteresis already wants the four children preload would ask for; 1.15 costs about 7% over 1.0 and buys a margin of 15% of the split distance before the deepest split. An earlier 2382 at 1.0 came from a replica that let no node be held split. Measure working sets with hysteresis-held splits: a camera that has just backed away leaves them in place.
- **`SurfaceMath.MaxNodeSizeSpread` is a hand-entered table, and each entry must be an upper bound.** π/2 for a tangent-adjusted cube sphere, √3 without the adjustment, exactly 1 for a plane grid, 1.02 for a cylinder (measured 1.01259). Too small an entry is a seam rather than a rounding error, because `LodMath` uses it to bound `MorphStartFraction`. `SurfaceGeometryTests.NodeSizeSpreadMatchesTheTable` re-derives all four numerically, as with the adjacency table and the handedness switch.
- **The morph runs in all four passes, and that is not optional.** `ForwardLit`, `ShadowCaster`, `DepthOnly` and `DepthNormals` each declare their own `Attributes`, so each needs `TEXCOORD2` (and `TEXCOORD3` where it uses a normal). Morphing only the forward pass leaves shadows and the depth prepass on the unmorphed geometry, which presents as shadow acne and depth-test dropouts along LOD boundaries — symptoms that look nothing like the cause. `GeomorphTests.ShaderMorphsInEveryPass` reads the shader source and checks, because the failure is silent.
- **The morph factor is computed from the UNMORPHED position.** `SonomaMorphFactor` takes `positionOS` before any lerp. That is what makes every pass agree on `k` for the same vertex, and what makes two chunks sharing a vertex agree: they compute the same world position for it, so the same distance, so the same `k`. Feeding it the morphed position would also be circular.
- **The morph measures distance from `_SonomaViewPosition`, never `_WorldSpaceCameraPos`, and that is not a style choice.** URP restores `_WorldSpaceCameraPos` for the main-light shadow pass explicitly — `MainLightShadowCasterPass` calls `ShadowUtils.SetCameraPosition`, commented "not set for passes executed before normal rendering" — and `AdditionalLightsShadowCasterPass` does not. So in a scene with a shadow-casting point or spot light and **no** shadowed directional light, the ShadowCaster pass reads whatever was last bound (a stale frame, or another camera) and casts from geometry at a morph state `ForwardLit` never drew: shadow acne along LOD boundaries, which is the same failure the "morph in every pass" rule exists to prevent, reached from the other side. `TerrainRoot.PushShaderGlobals` pushes the position once a frame, in render space, and `Update` hands *the same* `Vector3` to `LodSelector.Run` after adding the origin back — so selection and the morph cannot drift apart within a frame either. `GeomorphTests.ShaderMorphsInEveryPass` asserts it on `SonomaMorphFactor`'s body rather than the whole file, because the comment above the function names the builtin it is avoiding.
- **The main-light shadow coordinate must be computed per FRAGMENT, because the project runs cascades.** Under `_MAIN_LIGHT_SHADOWS_CASCADE`, `TransformWorldToShadowCoord` first calls `ComputeCascadeIndex` — a hard step across four camera-centred split spheres — and each cascade has its own matrix into its own quadrant of the shadow atlas. A shadow coordinate is therefore *not* an interpolatable quantity: a triangle whose vertices straddle a split sphere interpolates between two unrelated atlas tiles, samples a depth belonging to neither, and fails the compare. `SonomaTerrainTriplanar` computed it in the vertex stage unconditionally from M2 until 2026-09-07, which drew **one thin black ring per cascade boundary, concentric and following the camera** — at `SampleScene`'s shadow distance of 50 and the default 4-cascade splits, rings at roughly 6, 15 and 27 m. URP's own name for "the cheap per-vertex path is valid here" is `REQUIRES_VERTEX_SHADOW_COORD_INTERPOLATOR`, and `Shadows.hlsl` defines it for `_MAIN_LIGHT_SHADOWS` and `_MAIN_LIGHT_SHADOWS_SCREEN` only — deliberately not for the cascaded variant. Match URP's `InitializeInputData` rather than inventing a shorter form. `ShaderShadowTests.ShadowCoordIsNotInterpolatedUnderCascades` guards it.
- **`GetMainLight(shadowCoord)` is the wrong overload; only `GetMainLight(shadowCoord, positionWS, shadowMask)` applies `GetMainLightShadowFade`.** That fade is what dissolves the shadow over the cascade border and to nothing at `m_ShadowDistance`. Without it shadows terminate at a hard circle at the shadow distance — a fourth camera-following ring, arriving with the three cascade ones and easily mistaken for them. `shadowMask` is `half4(1,1,1,1)`: nothing in this project is baked, so `CALCULATE_BAKED_SHADOWS` is never defined.
- **URP keyword pragmas rot silently, and Unity 6 rotted this one.** A keyword the pipeline enables but the shader never declares produces no warning — the shader simply gets the variant with that keyword off. URP 17 replaced the single `_SHADOWS_SOFT` with the quality tier `_SHADOWS_SOFT_LOW` / `_MEDIUM` / `_HIGH`, so a shader still declaring only `_SHADOWS_SOFT` renders single-tap hard shadows (maximum acne) no matter what Soft Shadows quality the URP asset asks for, and changing that setting appears to do nothing. Keep the ForwardLit pragma list in step with `Packages/com.unity.render-pipelines.universal/Shaders/Lit.shader`; `ShaderShadowTests.ShadowKeywordsMatchThePipeline` pins the current set.
- **`LodMath.Create` bounds `MaxDepth` above as well as below, and both failures past it are silent.** Past `NodeId.MaxAddressableDepth` (30), `Span` evaluates `1 << 31 == int.MinValue` and the UV accessors return small negative numbers, so a node lands somewhere plausible but wrong — the same trap `NodeId.Parent` guards at the other end. Past 31 the shader's 32-entry `_SonomaMorphRanges` runs out; its `clamp` bounds the read but does **not** degrade gracefully, because slot 31's range is centimetres wide, so the chunk is pinned at `k = 1` and drawn permanently morphed onto its parent rather than unmorphed. The constant lives on `NodeId` because that is what sets it, and is enforced in `LodMath.Create` because that is where configuration is validated — not in the `NodeId` constructor, which runs inside Burst jobs and on every `Child()` call.
- **`_SonomaMorphRanges` is a global array, not a `MaterialPropertyBlock`.** A per-chunk property block would break SRP batching, which is the entire reason the chunk's depth travels in `TEXCOORD2.w` as a vertex attribute rather than as a material property. It is declared outside `CBUFFER_START(UnityPerMaterial)`, alongside `_SonomaWorldOrigin`, and `TerrainRoot.PushMorphRanges` re-pushes it every frame — shader globals are process-wide, so anything else setting that name would otherwise leave the terrain morphing against someone else's distances.
- **Elevation morphs too, on the same `k`.** `TEXCOORD3.w` carries the geomorph target's elevation and the shader blends `TEXCOORD1.w` towards it. Not decoration: the elevation drives the band blend, so leaving it on the fine value while the geometry moves to the coarse one shifts the colour bands at exactly the moment the parent takes over — a colour seam where there is no geometric one. It costs 4 bytes a vertex, taking `TerrainVertex` to 80. `SonomaMorph` returns the factor it used so the caller blends the elevation without recomputing it.
- **Skirts are turned off by setting their drop to zero, not by removing the geometry.** `TerrainSettings.SkirtsEnabled` zeroes both `SkirtDepth` and `SkirtFraction` before they reach the scheduler, so the `4R` skirt vertices stay in the buffer and collapse flat against the edge. The vertex count, index buffer and layout are therefore identical either way, which is what lets the toggle be a runtime setting rather than a rebuild.
- **`SkirtDepth` is absolute metres, so a configuration spanning many depths needs `SkirtFraction` too — a share of each chunk's own measured relief.** The gap a skirt hides in a transient two-depth state shrinks with depth. On Earth at 5× relief it is under a metre at depth 19 and kilometres at depths 2–9, so `SampleScene`'s 2 m would hide nothing coarse. The cracks would show during a fast descent, exactly when origin jitter is being judged, and read as jitter. A long skirt is never *seen*: it drops along the heightfield's own direction, so it lies directly beneath its edge, underground, and shows only through a crack, which is its job. But it pads the chunk's culling bounds by the same length. (M4's plan first said a long skirt hangs out of hillsides; it cannot, and bounds bloat is the whole cost.)
  - **The rule.** Each chunk's drop is `ChunkMeshLayout.SkirtDrop(SkirtDepth, SkirtFraction, relief, ChordSag)` = `SkirtDepth + SkirtFraction × relief + ChordSag`. `ChunkMeshJob` measures the relief, max − min height over its R × R grid, before it writes the skirt, and returns the drop in `HeightBounds[2]`. `GeomorphTests.JobHangsTheSkirtItReports` runs the real job with a nonzero fraction and sag and holds every skirt bottom, and its morph target, exactly the drop below its top.
  - **`ChunkMeshLayout.ChordSag`** is the surface's part of the gap, not the terrain's. A neighbour g depths coarser, fully morphed, draws edge segments 2^(g+1) of this chunk's vertex spacings long: 16 at `SkirtDepthGap` 3. They cut under a sphere's curve (over it inside a cylinder) by `k c² / 8`, with every spacing taken at the nominal size times `SurfaceMath.MaxNodeSizeSpread`. It is added whole, not scaled by `SkirtFraction`, because it is geometry and the fraction is tuned to the terrain. `ChunkMeshLayout.SkirtChordSag` is the one rule the scheduler and the tests both call. It passes no sag to a scene with no fraction, so `SampleScene` keeps an absolute skirt. On Earth the sag is 1,310 km at depth 0, 20 km at depth 3 and under a centimetre from depth 14. On a smooth sphere it is the whole gap; `StressSceneTests.ChordSagCoversASmoothSurface` checks that it covers that gap, and that without it the gap is open.
  - **The measurement.** Real transient edges were built at each stress scene's real heights, macro layer and biomes included. There were 400 per depth and per depth gap of one, two and three, inside root quads and across them, with coarse sides down to the roots, each side at morph factors 0, ½ and 1. Net of `SkirtDepth` and its chord sag, the side above has to cover at most this share of its own relief: Earth 0.628, small planet 0.546, ring 0.760 and terrarium 0.479, all at a gap of three. The gap itself is at most 0.11 of a node size anywhere.
  - **The tail.** It grows with the sample, then levels. The worst of the first 50 edges per depth and gap was 0.48–0.64; the worst of 200 was already the worst of 400; and the 99th percentile is 0.545 or less everywhere. `SkirtFraction` is half again over each scene's worst, rounded up: 1 on Earth, the small planet and the terrarium, and 1.2 on the ring.
  - **The limitation.** This is a sample, not the whole population, which the rule "measure a relief tail over the whole population" asks for. Nothing reports an uncovered gap at runtime, so a retune that roughens the terrain should rerun the measurement. The probe is `StressSceneTests.TransientEdges` at a larger sample.
  - **The tests.** `StressSceneTests.SkirtCoversTheTransientGap` and `EarthScaleTests.SkirtCoversTheTransientGapAtEveryDepth` rebuild a sample of such edges, through `StressSceneTests.TransientEdges`, and check each side's skirt against it. Each takes every gap down to depth 6 and one gap per depth below, with the relief on every fourth vertex; coarser sampling is a lower bound on the relief, so the test is the stricter side. They also check that the absolute 1 m alone would leave most of the edges open, that some edges cross a root quad, and that each gap has a coarse side at the root. Building macro texels on demand is most of their cost: about 0.6 s for Earth, 1.2–1.5 s for the other three scenes and 0.5 s for `ChordSagCoversASmoothSurface` under .NET 8, several times that under the Editor's Mono. Moving the sampling onto the Burst `HeightSampleJob`, as `WorkingSetTests` does, is the remedy if that proves too slow.
  - **The old rule.** M4 to M5b made the drop a share of the nominal node size, sized against twice an estimated relief demand that stacked every worst case on one node. After the 5× relief that was 2.1–2.9 node sizes, on every chunk, plains included.
  - **No cap, and why.** PR #10's review capped that share at twice `TerrainHeightFunction.MaxAbsHeight`, because Earth's 2.9 node sizes hung a 30,000 km skirt from each root, through the planet and out of the far side, drawn from high orbit as a fin over the near hemisphere. The per-chunk rule dropped the cap. A measured relief can never exceed twice `MaxAbsHeight`, so capping the relief term does nothing. Capping the whole drop would clip `ChordSag` where it is largest, 1,310 km at Earth's depth 0 and 328 km at depth 1 against a 169 km cap, and reopen the curvature gaps there. The rule cannot make the fin: the longest drop it can hang is `SkirtDepth + SkirtFraction × 2 × MaxAbsHeight + ChordSag(d)`, largest at depth 0. That is 1,479 km on Earth against a 6,371 km radius, 424 km on the small planet against 1,593 km, 183 km on the ring against 1,593 km, and 5.6 km in the terrarium against 10 km. `StressSceneTests.NoSkirtReachesPastTheCentre` holds it under the radius at every depth of all five stress scenes. On a cylinder a skirt longer than the radius would be a curtain outside the ring larger than the ring.
  - **Culling bounds are the box round what the job drew.** `ChunkMeshJob` returns, in `VertexBounds`, the chunk-local box round every vertex and morph target, skirts included; a morphing vertex lies between the two, so the box holds every frame of the morph. `GenerationScheduler.Upload` sets it as the mesh bounds, which is exact because a chunk is placed by translation alone. They used to be a cube round the base anchor, `NodeWorldSize + 2 × (max |h| + drop)` on a side. That padded by the absolute elevation, kilometres on a 20 m chunk, so the deepest chunks' bounds were hundreds of times their size.
  - **What it bought.** Over 64 random chunks per depth, against PR #10's capped cube, the box's longest side fell to the following share:

    | | depth 0 | mid depth | deepest depth |
    |---|---|---|---|
    | Earth | 0.84 | 0.12 (depth 9) | 0.005 |
    | Small planet | 0.80 | 0.13 (depth 7) | 0.009 |
    | Ring | 0.64 | 0.15 (depth 5) | 0.008 |
    | Terrarium | 0.36 | 0.14 (depth 2) | 0.048 |

    The volume fell to 0.23 at Earth's depth 0 and to about a thousandth from depth 8. The mean skirt drop on Earth is 1,334 km at depth 0, mostly the gap-3 chord sag; 2.1 km at depth 8; and 6.2 m at depth 19, against 58 m before.
  - **`SampleScene`.** The drop is computed in double and narrowed once, and a scene with no fraction is passed no sag, so `SampleScene`'s skirts are `SkirtDepth` to the bit and its meshes are unchanged. `ChunkMeshLayoutTests.SkirtDropIsExactWithNoFraction` and `ConstantsMatchSampleScene` hold that. Its culling bounds do change, to the tighter vertex box, which moves nothing that is drawn.
- **`OctaveCount` has to grow with `MaxDepth`, and the symptom of it not doing so looks like a rendering bug.** `MaxOctave(d) = clamp(d + K0, 0, OctaveCount − 1)`, so once `d + K0` passes the last octave the band limit stops rising and the deeper depths subdivide ground with no new detail in it. On an Earth-sized sphere `K0` is 4, so depth 19 wants octave 23; at the `OctaveCount` of 20 everything else uses, it clamps to 19 — a 19.8 m finest wavelength over 0.62 m vertex spacing, and the last four depths are smooth. `EarthTerrainSettings` runs 24. `HeightParams.IsOctaveStarved(depth)` is the predicate, `TerrainRoot` warns at startup when `MaxDepth` is starved, and `EarthScaleTests.DeepestDepthIsNotOctaveStarved` pins the Earth configuration and the starvation of the old one. It is not a `Create`-time throw: a deliberately smooth world is a legitimate configuration.
- **The LOD configuration is per scene, and the Earth one is not a reversal of `SampleScene`'s.** The relief demand is `C × HeightScale / S0` and `S0` grows with the radius while `HeightScale` need not, so a 300 m sphere with 50 m of relief (`HeightScale/S0` 0.102) needs `SplitFactor` 4 and `MorphStartFraction` 0.09, while Earth at `HeightScale` 9000 (0.00087) cleared `SplitFactor` 3 at 0.15 about nine times over with `C` 15 -- until M5b's biomes and close-up roughness spent most of that room (see "The relief spectrum"). `C` at depth 19 is an estimate, not a measurement — a face there is 4^19 nodes — which is why it is 15, half again over the largest sampled value, and why the selector's end-of-session report of the roughest chunk is the arbiter. `EarthScaleTests.EarthConfigurationClearsTheReliefAllowance` asserts both directions: Earth's configuration clears Earth's terrain, and does not clear `SampleScene`'s.
- **`TEXCOORD1` is spoken for.** `SonomaTerrainTriplanar.shader` reads it as `(topoUp.xyz, elevation)`. The geomorph attributes live at `TEXCOORD2` (morph position + depth) and `TEXCOORD3` (morph normal + morph elevation); `ChunkMeshJob` has written the first three since M2, before anything read them. `TEXCOORD3.w` was added afterwards, when the elevation turned out to need morphing too - the one place the M2 layout guess came up short.
- **Skirts are `4R` vertices, one row per edge, and `8(R-1)` triangles.** Two triangles per skirt quad, four edges — a `4(R-1)` triangle count is the easy mistake and sizes the index buffer at half what it needs. The four edges are walked anticlockwise as seen from outside (South +u, East +v, North −u, West −v) so one triangle order serves all four. The prototype's reversed edge was **North**, not West as an earlier note here claimed.
- **`ChunkMeshLayout` is UnityEngine-free on purpose** so its arithmetic runs in the out-of-Editor test harness; `ChunkMeshBuffers` holds everything that needs `UnityEngine.Rendering`. Keep the split — it is what catches buffer-sizing bugs as test failures rather than as memory corruption.
- **The scheduler checks "still wanted" twice**, before scheduling and again on completion, and disposes unwanted results instead of showing them. This is the fix for the prototype's orphan-chunk leak, where a collapsed node stayed queued and later produced a chunk nothing referenced.
- **`GenerationScheduler.Enqueue` re-prices a node already in the queue, and the heap is indexed so it can.** Priority is `distance / NominalSize` and the camera moves, so the number a node was first sighted with is stale by the next frame. Returning early for an already-queued node — which is how M3b first shipped — left every preloaded chunk carrying the priority it was requested at, `PreloadFactor × SplitFactor` node sizes out; by the time the camera arrived and the tree was waiting on that node to split, it generated *after* every entry whose own stale priority happened to be smaller, including nodes the camera had since flown away from. That is the four-chunks-of-latency-per-subdivision symptom preload exists to remove, and it hid the same way the M3a preload defect did: the tree still converges, the swap stays atomic, coverage stays complete. `LodSelector.Want` therefore calls `Enqueue` every frame while a node's `Chunk` is null and stops once it is resident — which is also what keeps the steady-state frame free of heap traffic and `SelectorDoesNotAllocatePerFrame` passing. `_heapAt` maps node → slot and **every swap must maintain it**; all four of its assignments are load-bearing (deleting any one is caught by fuzzing the heap against a reference model). Pushing a duplicate entry and discarding stale pops is the obvious alternative and the wrong one: it grows the heap by the whole wanted set every frame. `LodSelectorTests.RequeueingAQueuedNodeRepricesIt` enqueues sixteen nodes in exactly the reverse of the order they should generate in, re-prices them, and asserts the arrival order.
- **The resident-budget warning tests the size of the wanted set, not what eviction managed to do.** `_nodes.Count > MaxResidentChunks` — `ReleaseUnwanted` has already dropped everything else, so `_nodes` *is* the set this frame wants resident. The first form asked "over budget **and** nothing could be collapsed", which cannot fire in the case it was written for: a tree deep enough to overrun its budget always has a collapsible sibling group somewhere, so the collapse succeeds, the count comes back under budget, and both halves go false while the build/evict/rebuild churn runs on in silence at a full Burst job and mesh upload per chunk per frame. Only a budget below the six root quads ever reached it. `LodSelectorTests.EvictionTakesCompleteSiblingGroups` drives 600 frames of exactly that churn, which is why the gap survived review of the code that produced it.
- **Jobs are `[BurstCompile(CompileSynchronously = true)]`**; `TerrainHeightFunction` and `LatticeNoise` carry no attribute because plain static methods compile as part of the calling job. `LatticeNoise`'s gradient table is a `switch`, not a `static readonly float3[]` — Burst cannot read a managed static array from a job and silently falls back if you give it one.

## Unity-Specific Best Practices for This Project

- **Jobs System**: `IJobParallelFor` for height sampling, `IJob` for mesh building
- **Burst Compilation**: Mark generation jobs `[BurstCompile(CompileSynchronously = true)]`. Plain static helpers they call need no attribute — they compile as part of the calling job; the attribute only matters for function pointers.
- **NativeCollections**: Use `NativeArray<T>` for passing data to/from jobs
- **Mesh writing**: `Mesh.AllocateWritableMeshData` on the main thread, fill it in the job, then `Mesh.ApplyAndDisposeWritableMeshData` with `MeshUpdateFlags.DontRecalculateBounds`. Set buffer parameters before scheduling.
- **ScriptableObjects**: All configuration data (biomes, generation profiles, global settings)
- **Custom Inspectors**: Create custom editors for complex configuration data
- **Gizmos**: Draw quadtree bounds, LOD levels, camera ranges for debugging
